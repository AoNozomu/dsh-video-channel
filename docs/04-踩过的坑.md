# 04 · 踩过的坑（照这个避）

按类别排，每条都有现象 + 原因 + 解法。

## 环境类

### 坑 1：装 RapidOCR 把语音服务搞崩了

**现象**
```
A module compiled using NumPy 1.x cannot be run in NumPy 2.2.6
from rapidocr_onnxruntime import RapidOCR  → 崩溃
语音服务 :8790 也挂了
```

**原因**
`rapidocr-onnxruntime` 依赖 `numpy>=2`，pip 会把 numpy 从 1.26 升到 2.x。
但那个 venv 里的 `onnxruntime 1.18.0` 是**用 numpy 1.x 编译的**，升 numpy 后直接崩。
如果这个 venv 还跑着语音服务（CosyVoice / 任何 onnx 模型），语音一起挂。

**解法**
**新建独立环境**，别碰原 venv：
```bash
C:\...\Python314\python.exe -m venv E:\ocr-env
E:\ocr-env\Scripts\python.exe -m pip install rapidocr-onnxruntime
```
把 `--ocr-python E:\ocr-env\Scripts\python.exe` 指过去。

**如果已经搞崩了**：
```bash
# 把原 venv 的 numpy 降回来
原venv\Scripts\python.exe -m pip install "numpy==1.26.4" --force-reinstall
# 再把 rapidocr 从那个 venv 卸掉
原venv\Scripts\python.exe -m pip uninstall -y rapidocr-onnxruntime opencv-python pyclipper Shapely
```

## OCR 类

### 坑 3：喂字幕条给 RapidOCR，返回 None

**现象**
```python
r, _ = engine("strip.png")   # strip 是 960×119 的细长条
print(r)                     # None
```

**原因**：RapidOCR 的检测模型需要完整的画面上下文，孤立的细长条它判断不出是文字。

**解法**：喂**整帧**，认完之后按 y 坐标丢上面的部分（见 `02-字幕区域.md`）。

---

### 坑 4：同一帧 Windows OCR 时好时坏

**现象**：同一帧裁两次，一次读出「水龙头在灯下滴答」，一次 0 识别。

**原因**：Windows OCR 对半透明字幕背景、淡入淡出动画敏感。

**解法**：换 RapidOCR（本项目的做法），或者同一帧 OCR 两次取并集。

---

### 坑 5：字幕只读出半句

**现象**：`[215s] 该是`（应该是「应该是」）、`[231s] 辶顿骂我跑不掉`（应该是「这顿骂我跑不掉」）

**原因**：
1. 分辨率不够（480 宽 → 字幕几十像素高）
2. 字幕淡入动画进行中（半透明）
3. Windows OCR 的错字

**解法**：
- `--ocr-width 960`（本项目的默认）
- 换 RapidOCR
- 相邻相似合并会挑最长的那条，能救回一部分

## 画面类

### 坑 6：画面去重把该留的丢了

**现象**：分镜图里剧情跳跃，中间少了片段

**原因**：`--diff` 阈值太大

**解法**：
```bash
--diff 3    # 更敏感，留更多帧（分镜图会变多，token 变贵）
```

**怎么判断阈值合不合适**：跑一段，看 `keptFrames / totalFrames`：
```
保留率 40-60%   正常
保留率 <30%     太激进，调小 --diff
保留率 >80%     太保守，调大 --diff
```

---

### 坑 7：片尾字幕混进台词

**现象**
```
[1605s] 怪思h龙！切换合集下具段继续观看
[1621s] 就算是魔王也只有70级      ← 下一集的台词
```

**原因**：`--end` 设得比正片结束晚，抽到了自动播放的下一集。

**解法**：先 `video_probe` 看时长，把 `--end` 卡在正片结束前一点。

---

### 坑 8：片头/staff 名单占满分镜图

**现象**：前几张分镜全是「KAI IKARASHI」「NETFLIX」这种片头字样。

**原因**：片头动画画面变化快，去重后还是留了很多。

**解法**：
- `--start` 跳过片头（实测这一集正片从 80s 开始）
- 或者接受这几张，反正只占几张图

## 台词 ↔ 画面 对齐类

### 坑 9：台词的时间码和画面不同步

**现象**：`where.mjs --grep "我是塔莉亚"` → 指向 1325s，但 1325s 的画面是另一个人

**原因**：
1. OCR 抓到了相邻的、停留时间重叠的字幕
2. `--step 1` 是每秒一帧，字幕在 1 秒内切换时会有偏差

**解法**：
- `where.mjs` 找到秒数后，**往前推 1-2 秒再截图**（字幕通常先出现、画面后切）
- 或者直接 `video_zoom` 看 `秒数-2` 到 `秒数+2` 这一段

---

### 坑 10：认错人（本项目最严重的坑）

**现象**：整段剧情人物全错。

**原因**：分镜图每格只有 480×270，金发少年和金发老头分不清。

**解法**：见 `03-认人规矩.md` —— **认人只靠放大后的单帧**，拿不准就问。

## 成本类

### 坑 11：把 45 张分镜全读了

**现象**：一集看下来几十万 token。

**原因**：分镜图一张约 1024 token，45 张就是 45K；如果连着读几集更夸张。

**解法**：**先读 `subtitles.txt`（约 4K token），只挑 5-10 张关键图看。**
```
台词：3.8K token，剧情能讲清
图：只挑 8 张 ≈ 8K token
合计约 11K ≈ 0.011 元
```

---

### 坑 11.5：**工具不限制你读几张 —— 限制必须你自己定**

坑 11 说的是"别全读"，但真正的问题是：**`scan-video.mjs` 只返回一个 JSON**

```js
console.log(JSON.stringify({ ok: true, outDir, sheets: 45 }))
```

**照片要你自己一张张 `read_image`。** 工具不知道你读了多少张，也不会拦你。
我们没有在命令行里加 `--max-images`，因为"要读几张"取决于你要干什么 ——
但**默认值必须是保守的**，所以 agent 的规则里必须写死：

> **一次最多读 3-5 张分镜图。** 需要更多 → 用 `where.mjs` 定位 + `video_zoom` 单帧放大。

实测对比（一集 27 分钟动漫，1640 秒，45 张分镜）：

| 读法 | token | 约合 |
|---|---|---|
| 只读 `subtitles.txt` | ~4.4K | 0.009 元 |
| 台词 + 3 张图 | ~7.7K | 0.015 元 |
| 台词 + 12 张图 | ~17.6K | 0.035 元 |
| **台词 + 45 张全读** | **~54K** | **0.108 元** |

**贵 12 倍，而多出来的 42 张对理解剧情几乎没有帮助** —— 剧情在台词里，画面只回答
"这一格长什么样"。

## 工具类

### 坑 12：PowerShell 写源码文件加 BOM

**现象**：`node --check` 报 `SyntaxError: Invalid or unexpected token`

**原因**：`Set-Content -Encoding UTF8` 在 Windows PowerShell 里会写 BOM（`EF BB BF`），
Node 读到 BOM 当成非法字符。

**解法**：用 `write` 工具或 Python 写文件，别用 `Set-Content`：
```python
io.open(path, "w", encoding="utf-8", newline="\n").write(s)   # 无 BOM
```

---

### 坑 13：ESM 里用 require

**现象**：`require is not defined in ES module scope`

**解法**：用 `import fs from 'node:fs'`，或者 `import { fileURLToPath } from 'node:url'` 拿路径。

### 坑 14：**整集扫描在前台跑 —— 会把你自己的 agent 卡死**

这是本项目最"阴"的一个坑，因为它不报错、不崩溃，只是**安静地把整个 agent 冻住**。

**现象**：

```
你的 agent 发起视频扫描 → 界面显示「正在运行命令 · Scan ep1 15:00-26:00」
                    → 25 分钟没有动静
                    → 这期间收到的所有消息全部堆进「插话队列」（28 条）
                    → 界面上的排队数字一直在涨
```

**原因**：整集扫描确实要 10-20 分钟（OCR 是 0.37 秒/帧，一集 1640 秒就是 10 分钟起步）。
如果它是**前台阻塞**执行的，agent 在这段时间里不能说话、不能回消息，
而所有进来的消息都会排队等着 —— 你看到的就是「排队 24 条、一直在加」。

**更糟的连锁**：消息堆到一定程度，agent 醒来会**重读一遍整个上下文**（含那 28 条），
如果它又顺手把 45 张分镜读了，那一次就是几十万 token。

**解法**（两条都要）：

```js
// 1. 长命令一律后台跑（任何超过 1 分钟的都算）
pwsh({ command: 'node scan-video.mjs ...', run_in_background: true })
// 然后照常聊天；用 job_output 收结果

// 2. 规则要写进 agent 的常驻提示里，不能只写在文档里
//    "超过 1 分钟的命令 → run_in_background: true"
```

**怎么判断"该用后台"**：**你自己都不确定要多久 = 就该用后台。**

**如果你在写类似的 agent 插件**：把「长任务必须异步」当成硬约束写进系统提示，
不要指望模型自己判断——它会老老实实地等，然后你就收获一个卡死的 agent。

## 快速自查清单

```bash
# 1. 环境对不对
E:\ocr-env\Scripts\python.exe -c "import rapidocr_onnxruntime; print('ok')"
node --check scan-video.mjs && echo ok

# 2. 抽一小段试
node scan-video.mjs video.mp4 --start 200 --end 260 --out /tmp/t

# 3. 看结果
head -20 /tmp/t/subtitles.txt          # 台词读出来了吗
ls /tmp/t/sheet-*.png | wc -l          # 图有多少张
cat /tmp/t/index.json | head -5        # 有没有 kind 字段（UTF-16 截断的坑，新版已修）

# 4. 认人（关键一步）
node where.mjs /tmp/t --grep "某句台词"   # 定位到格
ffmpeg -ss <秒> -i video.mp4 -frames:v 1 -vf scale=1100:-1 check.png   # 放大看脸
```
